# 개발 과정과 문제 해결

[프로젝트 소개](../README.md) · [공개 소스 안내](code-map.md) · [구현 버전과 검증 범위](technical-notes.md)

이 문서는 실차 개발 경험을 정리한 상세 기록과 공개 소스를 대조해 작성했습니다. 공개 링크로 확인할 수 있는 구현과 보관본에 설명된 확장을 구분합니다.

## 1. 초기 방향 문제 · 1 m 이동을 초기화 절차로 만들기

### 위치가 맞아도 방향이 어긋날 수 있었다

유아용 전동차를 개조하고 Ubuntu 노트북과 센서를 연결한 뒤, 지도 경로와 차량 방향의 기준을 통합하는 과정에서 초기 방향 문제가 있었습니다. 차량 기준 목표 경로를 만들려면 현재 위치뿐 아니라 지도에서 차량이 어느 방향을 향하는지도 필요합니다. yaw에 고정된 오차가 남으면 경로점의 상대 방향이 달라져 조향 판단에 영향을 줍니다.

### 실제 이동을 기준으로 방향 오프셋을 계산했다

경로계획기는 GPS 위치와 경로가 준비되면 시작 위치를 저장합니다. 시작점과 현재 위치의 직선거리가 1 m 미만인 동안 `(0, 0) → (0, 1)`의 차량 정면 경로를 내보냅니다. 기준을 넘으면 그때의 GPS 변위로 이동 방향을 구하고, EKF 방향과의 차이를 한 번 저장합니다.

```text
이동 방향     = atan2(y₁ − y₀, x₁ − x₀)
yaw 오프셋    = 이동 방향 − 보정 시점의 EKF yaw
이후 보정 yaw = 현재 EKF yaw + 고정한 오프셋
```

공개 코드의 `_imu_yaw`는 `/odometry/filtered`의 quaternion에서 읽은 값입니다. 보정 대상은 **IMU 정보를 반영한 EKF 방향을 경로계획에 사용하는 기준**입니다. 원시 IMU 메시지나 전체 TF를 수정하는 절차는 아닙니다.

[공개 코드의 초기화 분기](https://github.com/Khusla/HLFMA_2025/blob/48406564072bd34c5d223b7e9fb8b05a2381fa11/src/decision_making_pkg/decision_making_pkg/path_planner_node.py#L219)

### 보관본에서는 초기화 상태를 구동 계층까지 전달했다

상세 개발 기록의 실차 보관본에는 `correctioning` 상태를 경로 메시지로 전달하는 구현이 설명되어 있습니다. 초기 직진 중에는 구동 명령을 기본값 120에서 80으로 낮추고, 방향 정렬이 끝나면 일반 추종으로 전환하는 구성입니다. **80과 120은 구동 명령값이며 실측 속도가 아닙니다.** 공개 메시지 정의에도 상태 필드는 있지만, 공개 경로·동작계획 노드에서는 이 값을 보정 상태에 맞춰 전달하고 구동값에 적용하는 분기가 확인되지 않습니다.

기록에는 노드 시작 후 일정 시간이 지나면 당시 yaw를 0 기준으로 삼는 다른 구현도 남아 있습니다. 이동벡터 방식은 지도에서 실제로 움직인 방향을 기준으로 얻는다는 차이가 있습니다. 보관 폴더 이름만으로 두 방식의 개발 순서나 변경 날짜를 확정하지는 않습니다.

### 해결 경험과 정량 검증을 나누어 기록했다

초기 방향 문제를 1 m 전진 방식으로 해결했다는 개발 경험과, 이를 수행하는 코드가 함께 남아 있습니다. 보정 전후 각도 오차나 반복 성공률을 기록한 실험표는 확보하지 못했습니다.

여기서 1 m는 시작점과 현재점의 **GPS 직선 변위 조건**입니다. 누적 바퀴 이동거리나 정확히 1.000 m에서 멈추는 제어를 뜻하지 않습니다. 두 끝점의 위치 오차와 실제 직진성이 방향 계산에 영향을 주므로, 이 값을 최적 보정거리나 정량적인 정확도 보장으로 표현하지 않습니다.

## 2. 좌표 통합 · 지도 경로에서 조향 부호까지 기준 잇기

### 경로와 현재 위치의 변환 기준을 공유했다

CSV에는 위도·경도가 들어 있고, 경로계획은 미터 단위의 평면 좌표를 사용합니다. GNSS 위치 변환에 사용하는 `navsat_transform_node`의 `FromLL` 서비스로 CSV 경로도 변환해 기준을 공유하도록 구성했습니다. 변환한 점의 누적 길이를 구한 뒤, 같은 간격의 거리 좌표에서 x·y를 선형 보간합니다.

이 구조에서 점 간격 0.30 m는 경로 재샘플링의 기본 설정입니다. 위치 측정 정확도나 실제 추종 오차가 0.30 m라는 의미는 아닙니다.

[공개 경로 로더](https://github.com/Khusla/HLFMA_2025/blob/48406564072bd34c5d223b7e9fb8b05a2381fa11/src/gps_path/gps_path/test_path_node1.py)

### 차량 기준 축과 명령의 부호를 연결했다

현재 위치를 뺀 경로점의 상대변위를 `(dx, dy)`, 보정 방향을 `ψ`라고 하면, 공개 코드의 변환은 다음과 같습니다.

```text
x_local = sin(ψ) × dx − cos(ψ) × dy
y_local = cos(ψ) × dx + sin(ψ) × dy
```

이 프로젝트의 경로 메시지에서는 오른쪽이 +x, 전방이 +y입니다. 예를 들어 지도 +x 방향을 보고 있을 때, 지도상 전방 점 `(dx > 0, dy = 0)`은 차량 좌표 `(0, +y)`로 바뀝니다. 지도상 왼쪽 점은 음의 local x가 됩니다. 이 축 약속에 맞춰 제어 노드는 `atan2(x_target, y_target)`로 상대 목표 방향을 계산합니다.

상위 조향은 좌우 1~5단계와 중앙 0으로 나뉩니다. 보관된 Arduino 제어 기록에서는 이 단계가 포텐시오미터 목표값으로 매핑되고, 현재 조향 위치와의 오차에 따라 모터를 움직입니다. 지도 좌표, 차량 기준 축, 조향 단계, 하위 구동 부호를 함께 맞춰야 하는 구조입니다.

[차량 기준 좌표 변환](https://github.com/Khusla/HLFMA_2025/blob/48406564072bd34c5d223b7e9fb8b05a2381fa11/src/decision_making_pkg/decision_making_pkg/path_planner_node.py#L408) · [목표 방향과 단계 조향](https://github.com/Khusla/HLFMA_2025/blob/48406564072bd34c5d223b7e9fb8b05a2381fa11/src/decision_making_pkg/decision_making_pkg/motion_planner_node.py#L283)

## 3. 디버깅 · 계산한 방향과 목표 경로를 함께 관측하기

방향 보정이 주행 계산에 사용되면, 시각화도 같은 보정 방향을 받아야 상태를 해석하기 쉽습니다. 경로계획기는 `/path_planner/yaw_corrected`를 발행하고, 시각화 노드는 GPS 위치와 이 방향을 받아 현재 자세·방향 화살표·전방 경로를 구성합니다.

| 관측 출력 | 확인하려는 내용 |
|---|---|
| `/pp/current_pose` | 현재 위치와 보정 방향 |
| `/pp/current_heading` | 차량이 바라보는 방향의 화살표 |
| `/pp/preview_path` | 차량 기준 경로를 지도 주변 좌표로 되돌린 모습 |
| 경로계획 CSV 로그 | 경유점 인덱스, 횡편차, 방향 오차, 목표점 거리, 복구 이벤트 |

이 표는 계산 상태를 확인할 수 있도록 만든 도구와 출력입니다. 당시의 모든 시험이 통과했다는 기록을 의미하지는 않습니다. 특히 표시 프레임과 계산 프레임을 함께 확인해야 합니다. 시각화에서 위치에 TF 변환을 적용하더라도 별도로 받은 yaw에 프레임 간 회전이 자동 반영되는 것은 아닙니다.

[시각화 코드](https://github.com/Khusla/HLFMA_2025/blob/48406564072bd34c5d223b7e9fb8b05a2381fa11/src/debug_pkg/debug_pkg/gps_path_visualizer_node.py) · [경로계획 로그 항목](https://github.com/Khusla/HLFMA_2025/blob/48406564072bd34c5d223b7e9fb8b05a2381fa11/src/decision_making_pkg/decision_making_pkg/path_planner_node.py#L123)

## 4. 보관본에 남아 있는 확장 구현

다음 내용은 상세 개발 기록이 분석한 실차·시뮬레이션 보관본을 요약한 것입니다. 공개 커밋에서 모두 확인되는 기능 목록과는 다릅니다.

| 다룬 문제 | 보관 기록의 구현 | 결과를 해석할 때의 범위 |
|---|---|---|
| 구간마다 경로와 진행 방향이 달라짐 | 일반 경로와 대안 경로를 나누고, 말단에서 대기·경로 선택·전진/후진 상태 전환 | 코드의 상태 전이 기록. 대회 미션별 성공률은 별도 자료 없음 |
| 카메라에 보이는 신호를 위치 조건과 연결 | 지정 신호등 지점의 반경 안에서 빨강·노랑이면 구동 명령을 0으로 변경 | 초록 확인 후에만 출발하는 로직으로 일반화하지 않음 |
| 후진 전환 시 명령이 갑자기 바뀔 수 있음 | 직전 목표 유지 시간, 조향 단계 변화 제한, 별도 후진 구동값 | 완전한 안정화가 검증되었다는 뜻은 아님 |
| 단계 조향을 실제 기구 위치로 전달 | Arduino에서 포텐시오미터 목표와 현재값의 오차에 따라 조향 모터 출력 | 조향 위치 피드백. 차량 속도 피드백·PID 성능과 구분 |
| 실차형 입력을 가상 환경에서 관찰 | Gazebo HENES 모델, 가상 GNSS, ROS 센서·명령 브리지, 경로 미리보기 | 시뮬레이션 구성 기록. 실차와의 추종 오차 비교 결과는 미확인 |
| 데이터 형식과 경로 형상 확인 | 위도·경도 열과 구분자 차이를 확인하고 저장점을 상대 좌표로 표시 | 저장 경로의 분석이며 실제 차량 궤적은 아님 |

### 저장 경로를 읽어 확인한 것

상세 기록의 데이터 분석에서는 `c1.csv`에 유효 좌표 201개, `real1.csv`에 215개가 있으며 처음 110개 점이 같은 순서로 일치한다고 정리되어 있습니다. 이 결과는 큰 경로와 일부 구간이 바뀐 경로를 비교하는 근거입니다. 실제 주행거리·완주 횟수·추종 정확도를 나타내지는 않습니다. 이번 포트폴리오 정리에서는 해당 보관 원본을 다시 계산한 결과로 제시하지 않습니다.

일부 파일은 탭과 쉼표가 섞여 있고, 헤더 이름과 전체 행을 감싼 따옴표도 달랐습니다. 따라서 좌표 기준을 맞추기 전에 입력 형식과 위도·경도 열을 확인해야 한다는 점이 기록에서 드러납니다. 독립 분석에서 읽어 낸 좌표 수와 당시 경로 로더가 정상 처리한 행 수는 구분했습니다.

## 확인된 성과와 남아 있는 자료

장려상 수상, 차량 개조와 노트북 탑재, 초기 방향 문제를 이동벡터로 해결한 경험을 중심으로 프로젝트를 설명합니다. 공개 소스는 방향 보정·경로 변환·명령 생성·관측 출력의 구체적인 구현을 뒷받침하고, 상세 기록은 보관본의 미션 처리·하위 제어·시뮬레이션 구성을 보완합니다.

주행 시간, 반복 완주율, 경로 오차 RMSE, RTK 고정해 유지율, 신호등 인식 정확도는 현재 확보한 근거로 수치화하지 않았습니다. 기록에 적힌 타이머·거리·명령값과 저장 데이터 분석값은 각각의 의미로만 사용합니다.
